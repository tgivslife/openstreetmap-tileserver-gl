# Installation

TileServer GL ships in two flavours:

| Image                   | Dockerfile        | Server-side rasterization              | Native deps                                   |
|-------------------------|-------------------|----------------------------------------|-----------------------------------------------|
| `tileserver-gl`         | `Dockerfile`      | yes (MapLibre GL Native + sharp/canvas) | GL stack, Xvfb, cairo/pango/rsvg, sqlite3     |
| `tileserver-gl-light`   | `Dockerfile_light`| no                                      | sqlite3 only                                  |

The light image serves vector tiles, styles, fonts, sprites and the web viewer, but no
`/styles/<id>/<z>/<x>/<y>.png`, no `/styles/<id>/static/...` and no elevation queries.
Light mode is selected by the package name ending in `-light`, which makes `src/server.js`
load the no-op stubs in `src/serve_light.js` instead of `src/serve_rendered.js`.

## Docker (recommended)

Build from this directory:

```bash
# full image (raster rendering)
docker build -f Dockerfile . -t stsdockerhub/tileserver-gl:<ver>

# light image (vector tiles only, much smaller)
docker build -f Dockerfile_light . -t stsdockerhub/tileserver-gl:<ver>-light
```

Run it with a data directory mounted at `/data`:

```bash
docker run --rm -it -v $(pwd):/data -p 8080:8080 stsdockerhub/tileserver-gl:<ver>
```

Additional options (see [USAGE.md](2.USAGE.md)) are appended to the end of the command:

* `docker run ... tileserver-gl --file my-tiles.mbtiles` — explicitly pick the tile file (when the folder holds more than one)
* `docker run ... tileserver-gl --verbose` — see the config that was created automatically
* `docker run ... tileserver-gl --config /data/config.json` — use an explicit configuration file (default: `config.json`)

### Building on Windows

`docker-entrypoint.sh` must keep LF line endings. If git checks it out with CRLF (the default when
`core.autocrlf=true`), the shebang becomes `#!/bin/bash\r`, Linux looks for an interpreter by that name and
the container dies at startup with the misleading:

```
exec /usr/src/app/docker-entrypoint.sh: no such file or directory
```

The repository's `.gitattributes` pins `*.sh` to `eol=lf`, so a fresh clone is fine. A clone made before that
file existed still has the CRLF copy — fix it once with:

```bash
git add --renormalize .
git checkout -- tileserver-gl/docker-entrypoint.sh
```

Verify with `git ls-files --eol tileserver-gl/docker-entrypoint.sh`, which should report `i/lf w/lf`, then
rebuild the image.

Notes on the images:

* Both images run as the unprivileged `node` user, declare `VOLUME /data`, `WORKDIR /data` and expose port `8080`.
* `HEALTHCHECK` runs `src/healthcheck.js`, which polls `http://localhost:8080/health`. Because that URL is
  hard-coded, do **not** change the in-container port with `--port` — map the port on the host instead
  (`-p 9000:8080`).
* The entrypoint starts `Xvfb` on `DISPLAY=:99` when it is present (full image only) and then execs `node`.
  If the first argument is itself an executable it is run instead, so `docker run --rm -it <image> bash`
  gives you a shell in the container.
* jemalloc is preloaded (`LD_PRELOAD`, `MALLOC_CONF`) to keep long-running renderer memory in check.

## From source

Requirements:

* Node.js `^20.19.0 || ^22.13.0 || 24` (see `engines` in `package.json`; `.nvmrc` pins the version used in CI)
* A C++ toolchain for the native addons (`sqlite3`, and for the full install also `canvas` and
  `@maplibre/maplibre-gl-native`)

On Ubuntu 24.04 the build dependencies are:

```bash
sudo apt-get install -y build-essential python3-setuptools pkg-config xvfb \
  libglfw3-dev libuv1-dev libcairo2-dev libpango1.0-dev libpng-dev \
  libjpeg-dev libgif-dev librsvg2-dev libcurl4-openssl-dev libicu-dev
```

Then:

```bash
npm ci                 # or `npm ci --omit=dev` for a runtime-only install
node src/main.js --config config.json
```

`npm ci` runs the `prepare` script, which copies the MapLibre GL JS, MapLibre GL Inspect, Leaflet and
mapbox-gl-rtl-text browser bundles into `public/resources/`. Those bundles are what the viewer templates
load, so a checkout without `prepare` having run will serve a broken viewer.

Server-side rendering needs an X server. Headless machines should run the process under `xvfb-run`:

```bash
xvfb-run --server-args="-screen 0 1024x768x24" node src/main.js --config config.json
```

## Development

```bash
npm test            # mocha suite (needs a display; use `npm run test-docker` for xvfb-run)
npm run lint:js     # eslint
npm run lint:js:fix
npm run lint:yml
```

`npm run test:visual:generate` regenerates the static-image fixtures under `test/fixtures/`.
